# Tratamento de Erros — EasyPDV

| Cenário | Comportamento | Recuperação |
|---|---|---|
| Intermediador/Bling indisponível | Venda segue normal, nunca bloqueia | `SyncOutboxWorker` local retenta a cada 15s (teto de 5 tentativas); no Intermediador, BullMQ retenta o job (5 tentativas, backoff exponencial); após esgotar, fica "failed" e visível na Central de Erros de Sincronização (`GET /sync/outbox?status=failed` / `GET /sync/jobs?status=failed`) — retry manual via `POST .../retry` |
| Redis indisponível / perda de job em fila (Intermediador) | Sync fica represada, venda local não é afetada | **Resolvido na Sprint 8**: `SyncJobReconciliationWorker` varre a cada 2min por `SyncJob`s travados em "processing" há mais de 5min (worker morreu ou Redis perdeu o job no meio do processamento — cenário estreito, já que falha normal da API já resolve pra "failed" via BullMQ) e marca "failed" com `lastError` explicando o motivo. Não reenfileira sozinho — aparece na Central de Erros pra reconciliação manual, por design (ver ROADMAP.md: "Central de Erros de Sincronização — reconciliação **manual**") |
| Produto sem estoque | Alerta visual, mas permite prosseguir | Relatório de divergência para ajuste manual |
| Pagamento recusado | Registrado como `recusado`, venda aguardando | Operador tenta outra forma — fluxo normal |
| Venda duplicada | Prevenida por chave de idempotência gerada no frontend | Reenvio com a mesma chave retorna o resultado já processado |
| Token expirado | 401 → renovação automática via refresh token; falha total força login | Carrinho em memória não pode ser perdido durante a reautenticação |
| Timeout | Não significa "falhou", significa "incerto" — resolvido pela idempotência | Reenviar é seguro |
| Conflito de sincronização (preço divergente Bling×local) | Nunca sobrescreve silenciosamente — gera item de revisão manual | Central de Erros de Sincronização |
| Falha de conexão PDV local ↔ Intermediador | Só afeta sincronização, nunca a venda em si | Fila local aguarda reconexão |
| Falha na emissão de NFC-e (Sprint 12) | Nunca marca o `SyncJob` como failed nem bloqueia o pedido de venda já criado — "fiscal pode esperar" | `FiscalDocument` (Intermediador) fica com `status=error` + `errorMessage`; visível via `GET /fiscal/sale/:saleId`; sem retry automático nesta sprint, comprovante não-fiscal (ESC/POS, Sprint 11) segue sendo o que sai na hora |

**Resolvido na Sprint 5:** concorrência na baixa de estoque (dois caixas confirmando venda do mesmo produto ao mesmo tempo) foi resolvida sem lock explícito — `PrismaSaleRepository.confirm()` usa `StockItem.update({ quantity: { decrement: n } })`, que o Prisma traduz num `UPDATE ... SET quantity = quantity - n` atômico no SQL, e a serialização de escritas do próprio SQLite garante que as duas transações não se intercalem. Validado empiricamente disparando duas confirmações simultâneas do mesmo produto (5 unidades cada, estoque inicial 60): resultado final 50 (60-5-5), com dois `StockMovement` distintos — nenhuma escrita perdida. Ver [DATABASE.md](./DATABASE.md).

**Gap conhecido desde a Sprint 6:** `POST /sync` (Intermediador) não tem autenticação nenhuma — qualquer requisição consegue criar/consultar `SyncJob`s. Aceitável só porque provisionamento de terminal e autenticação PDV local ↔ Intermediador ainda não existem (Sprint 10 / risco aberto — ver `Claude/Projetos/EasyPDV/Decisões e Riscos Abertos.md` no cofre Obsidian); precisa ser fechado antes de qualquer deploy real no Railway. Os endpoints `/integrations/bling/*` (Sprint 7) têm o mesmo gap.

**Validado contra a API real do Bling na Sprint 7** (produto de teste real: pedido de venda criado, conferido campo a campo contra a API): `GET /produtos?codigo=`, `GET/POST /contatos` e `POST /pedidos/vendas` funcionam como documentado publicamente. Uma suposição inicial não se confirmou: **Bling não expõe endpoint de listagem de formas de pagamento** — o id (`BLING_DEFAULT_PAYMENT_METHOD_ID`) precisa ser obtido manualmente no painel do Bling (Configurações > Formas de Pagamento) ou inspecionando um pedido existente via `GET /pedidos/vendas/:id`, e configurado como variável de ambiente. **Simplificação V1 documentada**: todo pedido criado no Bling usa essa única forma de pagamento configurada, independente da forma real usada na venda local (dinheiro/cartão/pix) — mapear as formas de pagamento locais para IDs reais do Bling fica como refinamento futuro, não bloqueia a V1.

**Emissão de NFC-e via Bling (Sprint 12), pesquisada contra a API real antes de implementar** (mesma metodologia da Sprint 7): `POST /pedidos/vendas/:id/gerar-nfce` gera a NFC-e a partir do pedido de venda já criado — o Bling resolve os dados fiscais (NCM/CFOP/CST etc.) do cadastro do produto do lado dele, sem precisar desses campos no schema local. Isso só cria um rascunho ("Pendente"); `POST /nfce/:id/enviar` é quem de fato transmite pra SEFAZ. Emissão é **opt-in via `BLING_NFCE_AUTO_EMIT`** (env var no Intermediador, default desligado) — decisão deliberada: emitir NFC-e é uma ação fiscal real, diferente de criar um "pedido de venda" de teste; sem essa flag, conectar o Bling numa loja nova (ou testar em dev) não dispararia documentos fiscais reais sem o lojista/operador confirmar que a conta Bling está configurada pra NFC-e (certificado, inscrição estadual). Ver Decisões e Riscos Abertos no cofre Obsidian.

**Bug de idempotência corrigido antes de existir de fato (Sprint 12)**: adicionar a emissão de NFC-e depois da criação do pedido de venda abriu uma janela nova de retry-após-sucesso-parcial que não existia antes (`createSalesOrder` não é idempotente, ver Sprint 8 abaixo) — se a etapa de NFC-e falhasse e o `SyncJob` fosse reprocessado, o pedido de venda seria criado de novo. Corrigido checando o `ErpSyncMapping` (sale→externalId) **antes** de chamar `createSalesOrder`, não só depois — mesmo padrão já usado pra produto/contato, só que essa checagem estava faltando pro pedido de venda em si.

**Bug real encontrado e corrigido na Sprint 8** (testado com duas requisições concorrentes de verdade, não hipotético): `POST /sync/jobs/:id/retry` chamado duas vezes em sequência rápida (ex: duplo clique) enfileirava **dois jobs BullMQ em paralelo processando o mesmo `SyncJob`** — como `createSalesOrder` no Bling não é idempotente, isso podia criar pedidos duplicados. Corrigido trocando o reset de status por um `UPDATE` condicional atômico (`WHERE id=? AND status='failed'`, checando `count > 0`) em vez de `findById` + `update` incondicional — a mesma correção foi aplicada em `POST /sync/outbox/:id/retry` no PDV local por consistência, mesmo a corrida lá sendo bem mais branda (sem fila, o worker só processa a entrada uma vez por tick).
