# Arquitetura Electron — EasyPDV

`apps/electron` — shell desktop que empacota `pdv-frontend` (export estático) + `pdv-backend` (processo local) num único instalador Windows. Implementado na Sprint 10.

## Processos

- **Main** (`src/main/index.ts`) — único com acesso a hardware (impressora, gaveta, leitor, Sprint 11), gerencia a janela, spawna o `pdv-backend` como processo filho, decide entre a UI de ativação e o app real, e roda o auto-update.
- **Renderer** — o build estático de `pdv-frontend` (uma vez ativado) ou `resources/activation.html` (antes da ativação), `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`.
- **Preload** (`src/preload/index.ts`) — `contextBridge` expondo só funções nomeadas (`window.easypdv.*`), nunca `ipcRenderer` cru. Se aplica às duas páginas (mesma `BrowserWindow`).

## Como o pdv-backend é iniciado

`startBackend()` spawna `dist/main.js` do pdv-backend como processo filho via `spawn(process.execPath, [entry], { env: { ELECTRON_RUN_AS_NODE: "1", ... } })` — `ELECTRON_RUN_AS_NODE` faz o próprio binário do Electron rodar como um Node.js puro, então **não precisa de uma instalação separada de Node no PC do cliente**. `DATABASE_URL` é montada em runtime apontando pra `app.getPath("userData")/easypdv.db` (SQLite por instalação, fora da pasta somente-leitura do instalador) e injetada explicitamente no `env` do processo filho — nunca depende de um `.env` empacotado. `JWT_SECRET` (`IdentityModule` exige via `getOrThrow`) é gerada uma vez por instalação (`crypto.randomBytes(48)`) e persistida em `app.getPath("userData")/jwt-secret`, reaproveitada entre boots — nunca hardcoded no código-fonte (senão toda instalação do EasyPDV compartilharia a mesma chave de assinatura de token).

O próprio `pdv-backend` (`src/main.ts`, `runMigrations()`) roda `prisma migrate deploy` contra esse `DATABASE_URL` antes de escutar a porta — idempotente, roda em todo boot. É assim que cada instalação nova se automigra sozinha no primeiro boot (ou quando uma versão nova do app traz uma migration nova), sem o instalador precisar rodar `prisma migrate dev` manualmente em cada loja. Logo em seguida, `ensureAdminUser()` garante pelo menos um Administrador (`count()>0` sai sem fazer nada — idempotente, mesma lógica de `prisma/seed.ts`, mas só a parte do admin: `prisma db seed` inteiro é fixture de dev, catálogo/depósito de exemplo não devem ir pra produção). Sem isso, um install novo não teria usuário nenhum e ninguém conseguiria logar. `createWindow()` só acontece depois de `waitForHealth()` confirmar `GET /health` respondendo.

**Risco aberto conhecido**: o admin nasce com `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD` (default `admin@easypdv.local`/`troque-esta-senha`) — mesmo placeholder do seed de dev, sem troca obrigatória no primeiro login. Toda loja nova nasce com a mesma senha conhecida publicamente até esse fluxo ser construído (ver Decisões e Riscos Abertos no cofre Obsidian — risco #8, não bloqueia dev/teste mas bloqueia venda real).

## Provisionamento de terminal

No boot, o Main consulta `GET /provisioning/status` no backend local recém-subido:
- **`activated: false`** → carrega `resources/activation.html` (página HTML standalone, vanilla JS — não faz parte do build do Next.js). O operador digita o código de ativação gerado por um Administrador (`POST /organizations/:id/activation-codes` no Intermediador); a página chama `POST /provisioning/activate` no backend local, que troca o código por uma identidade de terminal + apiKey no Intermediador (`POST /terminals/activate`) e persiste tudo em `StoreIdentity` (SQLite, uma linha só). Ver docs/DATABASE.md.
- **`activated: true`** → carrega o export estático de `pdv-frontend` direto.

Depois de ativar, a página chama `window.easypdv.activationCompleted()` (preload → IPC `activation:completed`) — é o Main, não a própria página, quem decide trocar pra janela do app real (`mainWindow.loadFile(resolveFrontendIndex())`); a página de ativação não tem esse poder sozinha (contextIsolation).

A apiKey retornada por `POST /terminals/activate` é o que `HttpSyncGateway` (módulo Sync do pdv-backend) anexa em todo `POST /sync` no Intermediador daqui pra frente — fecha o risco #6 documentado em Decisões e Riscos Abertos (autenticação PDV local ↔ Intermediador inexistente).

## Empacotamento

`pnpm --filter @easypdv/electron prepackage` (`scripts/prepare-resources.js`) roda antes de `electron-builder`, 7 passos:
1. `pnpm --filter @easypdv/pdv-backend build`.
2. `pnpm --filter @easypdv/pdv-backend run prisma:generate` — engine nativo da plataforma atual.
3. `pnpm --filter @easypdv/pdv-frontend build` — export estático (`next build`, `output: 'export'`). **Sempre roda aqui, sem checagem de "já existe"** — ver lição abaixo.
4. Empacota o `pdv-backend` num único arquivo via **esbuild** (não `pnpm deploy` — reescrito na Sprint de hardening pra reduzir contagem de arquivos do instalador, ~11.600 → ~5.000, ver Obsidian "Lição técnica registrada (2026-08-17)"). `@prisma/client`, `prisma` (CLI) e `bcrypt` ficam de fora do bundle (binários nativos / `require.resolve` em runtime).
5. Copia esses três pacotes externos + suas dependências transitivas resolvidas manualmente (sem depender do campo `exports` do `package.json`, fonte real de bugs — ver comentário no script).
6. Copia `prisma/schema.prisma` + `migrations/` (nunca `dev.db`/`.env`).
7. Copia o export estático de `pdv-frontend` (`out/`, gerado no passo 3) pra `resources-build/pdv-frontend`.

`electron-builder` (`pnpm --filter @easypdv/electron package`) usa `extraResources` pra copiar `resources-build/pdv-backend` → `resources/pdv-backend` e `resources-build/pdv-frontend` → `resources/pdv-frontend` no app empacotado (fora do `app.asar` — precisam existir como arquivos reais no disco pro Node spawnar/ler, `asar` tem limitações com binários nativos e child_process). `resolveBackendEntry()`/`resolveFrontendIndex()` no Main distinguem dev (`../../../pdv-backend`, irmão de `apps/electron`) de empacotado (`process.resourcesPath`).

**Testado de verdade nesta sprint, incluindo o `.exe` empacotado de verdade** (não só `pnpm start` em dev): banco SQLite novo criado em `app.getPath("userData")`, as 7 migrations aplicadas sozinhas do zero, Nest subindo, `/health` e `/provisioning/status` respondendo pro próprio Electron, `POST /auth/login` com o admin auto-criado devolvendo um token JWT real — em dev E rodando `EasyPDV.exe` do instalador gerado (userData limpo entre tentativas pra simular instalação genuinamente nova). Dois bugs reais só apareceram nesse teste do pacote final (ambos silenciosos em dev, mascarados pelo `.env` local) — o primeiro derrubava o boot com um diálogo de erro nativo do Electron, batizado e corrigido antes do segundo aparecer: `nestjs-pino` crashava no boot tentando carregar `pino-pretty` — esse transport só é usado quando `NODE_ENV !== "production"`, e o Electron nunca setava `NODE_ENV` ao spawnar o processo filho; `pino-pretty` é `devDependency` (formatação de log de terminal, sem uso num processo gerenciado pelo Electron) e `pnpm deploy --prod` corretamente a excluiu do bundle. Corrigido setando `NODE_ENV: app.isPackaged ? "production" : "development"` no `env` do `spawn()`. O segundo bug só apareceu depois de corrigir o primeiro e testar de novo: `JWT_SECRET` ausente (`.env` de dev removido do bundle, sem substituto) e nenhum usuário existente (seed de dev não roda em produção) — os dois já descritos acima e corrigidos com `resolveJwtSecret()` (Electron) e `ensureAdminUser()` (pdv-backend). Confirma a lição da Sprint 1 de novo: só testar em dev não prova que o pacote final funciona, e às vezes é preciso mais de uma rodada de teste-fix-teste pra achar tudo. Empacotamento real via `electron-builder` também esbarrou em duas limitações deste ambiente de desenvolvimento específico: rede instável pra `release-assets.githubusercontent.com` (contornado com `ELECTRON_OVERRIDE_DIST_PATH` apontando pro binário que o pacote `electron` já baixa sozinho) e falta de privilégio de symlink do Windows ao extrair ferramentas de assinatura de código não usadas (contornado com `signAndEditExecutable: false` + `CSC_IDENTITY_AUTO_DISCOVERY=false`, já que não há certificado de assinatura ainda). Nenhuma das duas deve ocorrer numa máquina de desenvolvimento normal com privilégios padrão.

**Bug real, achado testando o instalador de verdade (2026-08-18)**: `prepare-resources.js` copiava `apps/pdv-frontend/out` (passo 7) mas nunca o gerava — só checava se existia e abortava se não. Um fix de UI (`sale-view.tsx`) foi corrigido no código-fonte, mas **dois instaladores seguidos** empacotaram um `out/` de horas antes, porque `next build` nunca tinha rodado de novo nesse meio tempo — o usuário instalou, testou, e o bug continuava lá, mesmo com o commit certo. Confirmado comparando o mtime dos arquivos em `out/` contra o mtime do `.tsx` corrigido (`find out -newer sale-view.tsx` vazio = prova de que nada foi regenerado). Corrigido adicionando o `next build` como passo 3 do próprio `prepare-resources.js` — sempre roda, sem "se já existe, pula" (mesmo padrão do passo 1, que já sempre reconstrói o backend). Mesma família de bug já registrada duas vezes antes neste projeto (Sprint 10, `apps/electron/src/main` não reconstruído; hardening de 2026-08-17, `app.asar` não reempacotado) — reforça que **qualquer artefato consumido por cópia** (não gerado na hora) é candidato a ficar obsoleto silenciosamente se o script que empacota não force a regeneração.

## Auto Update

`electron-updater` (`src/main/auto-update.ts`), canal estável configurado via `build.publish` (GitHub Releases, `Chanciier/EasyPDV`) no `package.json`. Checagem no boot + a cada 4h. **Nunca aplica update com uma `CashSession` aberta em qualquer caixa do terminal** — `GET /provisioning/busy-status` (novo endpoint sem auth, Sprint 10) confirma antes de instalar; se ocupado, reavalia a cada 10min até liberar, em vez de esperar o próximo ciclo de 4h inteiro. Requer uma release real publicada no `publish` configurado pra fazer alguma coisa — sem isso, `checkForUpdates()` simplesmente não acha nada, não é testável ponta a ponta localmente.

**Publicação (2026-08-21)**: `.github/workflows/release.yml` builda o instalador Windows num runner `windows-latest` e publica automaticamente no GitHub Releases a cada push de tag `v*` (`electron-builder --publish always`, autenticado só com o `GITHUB_TOKEN` padrão do Actions — repositório público, sem segredo novo). Fluxo de lançamento: testar localmente como sempre (typecheck/lint/build + boot real) → `git tag vX.Y.Z && git push --tags` → CI builda e publica sozinho → terminais já instalados recebem a atualização sozinhos, sem reenvio manual do `.exe`. Achado real (2026-08-21, antes de ligar isso): toda a infraestrutura (`auto-update.ts`, `publish` no `package.json`) já existia desde a Sprint 10, só nunca tinha sido usada — `apps/electron/package.json` ficou travado em `version: "0.0.0"` (não comparável por semver) e nenhum release tinha sido publicado ainda.

## Provisionamento de terminal (Intermediador)

`apps/intermediador`: módulo `organizations` — `Organization`/`Store` (já existiam desde o Sprint 0) + `ActivationCode`/`Terminal` (Sprint 10). `POST /organizations/:id/activation-codes` gera um código de 8 caracteres (alfabeto sem 0/O/1/I/L), expira em 30min, uso único. `POST /terminals/activate` troca o código por um Terminal + apiKey (SHA-256 armazenado, texto puro só na resposta). `TerminalApiKeyGuard` protege `POST /sync` — o único endpoint do Intermediador com autenticação real até agora. Ver docs/API.md e docs/DATABASE.md.

## Hardware (Sprint 11)

Impressora e gaveta ficam atrás de uma interface interna comum no Main Process (`apps/electron/src/main/hardware/printer-driver.ts`, `PrinterDriver.print(bytes: Buffer)`) — trocar de fabricante/mecanismo não toca Renderer nem Preload. Duas implementações:
- **`WindowsRawPrinterDriver`** — envia os bytes pro spooler do Windows como datatype `RAW` via `resources/print-raw.ps1` (P/Invoke clássico de `winspool.drv`, padrão KB Q322090: `OpenPrinter`/`StartDocPrinter`/`WritePrinter`/...), chamado via `child_process.execFile("powershell.exe", ...)`. Escolhido deliberadamente em vez de um addon nativo Node (`node-printer`, `ffi-napi`) pra não introduzir uma dependência de compilação nativa não testada no ambiente real do cliente — só usa .NET já embutido no Windows.
- **`MockPrinterDriver`** — usada quando nenhuma impressora foi configurada em Settings, ou com `EASYPDV_PRINTER_MOCK=1`; loga os bytes em vez de imprimir de verdade. É o que permite testar a IPC ponta a ponta sem hardware físico.

`apps/electron/src/main/hardware/escpos.ts` monta os comandos ESC/POS mínimos (init, alinhamento, negrito, corte parcial `GS V 66 0`, pulso de gaveta `ESC p 0 25 250` no pino 2 — ligação mais comum de gaveta via kick-out integrado da impressora). Texto vai em ASCII puro (`stripAccents()`) porque térmicas ESC/POS usam code pages de 1 byte que variam por impressora/configuração, não UTF-8 — sem saber qual code page está configurada em cada impressora do cliente, remover acento é mais seguro que arriscar caractere ilegível. `receipt-formatter.ts` monta o cupom completo a partir de `ReceiptPrintPayload` (`packages/shared-types/src/electron.ts` — contrato único entre Renderer e Main).

**Cupom fiscal com QR code (Sprint 14)**: `escpos.ts` ganhou `qrCode()` — família de comandos `GS ( k` (Epson, símbolos 2D: seleciona modelo → tamanho do módulo → nível de correção de erro → grava os dados → imprime). `receipt-formatter.ts` ganhou `buildFiscalReceipt()`, chamado só quando `ReceiptPrintPayload.fiscal` está presente (disparado manualmente pelo operador no Histórico, nunca no fluxo automático de confirmação — esse continua sempre `buildReceipt()` não-fiscal, decisão já travada do projeto: "cliente sempre sai com papel na hora, o documento fiscal de verdade pode chegar em seguida"). `payload.fiscal.qrCodeUrl` vem pronto do Intermediador, extraído do XML autorizado do Bling (`<infNFeSupl><qrCode>`) — o Main process nunca reconstrói essa URL, só desenha o QR code com o conteúdo que já chegou pronto.

Canais IPC (convenção `domínio:ação` já estabelecida): `printer:print`, `drawer:open`, `printers:list` (via `Get-Printer`), `settings:get`, `settings:set`. `HardwareSettings` (`printerName`, `autoPrintReceipt`, `autoOpenDrawerOnCash`) persiste em `app.getPath("userData")/settings.json`, mesmo padrão de `resolveJwtSecret()` (Sprint 10). `print-raw.ps1` vai em `extraResources` (fora do `app.asar`, igual `pdv-backend`/`pdv-frontend`) — um processo externo (`powershell.exe`) não lê de dentro do asar.

No `pdv-frontend`: `hooks/use-hardware.ts` expõe os canais via `window.easypdv` com guarda de ambiente (`isElectron()` — fora do Electron, `window.easypdv` é `undefined`; hardware é sempre opcional, nunca bloqueia a venda). `components/pos/settings-dialog.tsx` (aberto pelo ícone de engrenagem no rodapé da sidebar, `pos-shell.tsx`) deixa escolher a impressora entre as cadastradas no Windows, os dois toggles de automação, e tem botões "Imprimir teste"/"Abrir gaveta" pra validação manual assim que o hardware físico for conectado. `sale-view.tsx` dispara impressão/abertura de gaveta automaticamente na confirmação da venda quando os toggles correspondentes estão ligados — como `mutate()` (não `mutateAsync()`), nunca bloqueia nem falha a venda já confirmada no backend.

Leitor de código de barras USB (emulação de teclado) é capturado direto pelo Renderer, sem IPC nem Main — só faz sentido na tela Venda, então o listener vive no próprio `sale-view.tsx` (desmontado quando a tela muda). Sem nenhum input/select/textarea focado e nenhum diálogo de pagamento/recibo aberto, o primeiro caractere digitado foca a busca e é encaminhado manualmente (`setTerm(prev => prev + char)` + `searchRef.current.focus()`); o resto do código + Enter chega direto no input, reaproveitando o fallback de leitura exata que já existia (`findProductByBarcode`). **Bug real encontrado e corrigido rodando de verdade no navegador**: sem `e.preventDefault()` no handler, mover o foco pro input *dentro* do mesmo evento de keydown fazia o navegador aplicar a inserção nativa de texto no elemento recém-focado — duplicando o primeiro caractere (`"77"` em vez de `"7"`). Corrigido chamando `preventDefault()` antes de mudar o foco.

**Testado de verdade nesta sprint**: impressão raw via WinSpool contra a impressora de referência de verdade (`ELGIN L42PRO FULL`, cadastrada no Windows desta máquina via USB) — `WritePrinter` retornou sucesso e o job apareceu na fila real de impressão do Windows como "EasyPDV Raw Print" (`Get-PrintJob`, depois limpo com `Remove-PrintJob`). A impressora física ainda não está conectada nesta máquina (só será conectada quando o usuário tiver acesso ao terminal/PDV) — confirmação visual de papel saindo/corte/pulso de gaveta continua pendente até lá, é um risco aberto conhecido, não um bug. Fluxo completo testado ponta a ponta no navegador (`next dev`, sem Electron — só o que dá pra testar sem o bridge real): Settings mostra corretamente a mensagem de indisponibilidade fora do Electron com "Salvar" desabilitado; leitura de um código de barras real do catálogo de seed (`7891000000011`, "Arroz 5kg") via foco automático + digitação simulada resultou no item certo adicionado ao carrinho; venda completa (pagamento em dinheiro, confirmação, cupom) sem erros — os hooks de impressão/gaveta viram no-op silencioso fora do Electron, como projetado.

## Backup local (Sprint 15)

`apps/electron/src/main/backup.ts` — cada loja é um único arquivo SQLite (`resolveDatabasePath()`, `app.getPath("userData")/easypdv.db`) sem nenhuma cópia até esta sprint; um arquivo perdido ou corrompido era perda total dos dados daquela loja. Escopo confirmado com o usuário: **local automático + restaurar manual**, sem envio pra nuvem/Intermediador (fica pra uma rodada futura).

- **`createBackup()`**: copia o `.db` pra `app.getPath("userData")/backups/easypdv-<timestamp>.db` e, defensivamente, também os sidecars `-wal`/`-shm` se existirem — **desde 2026-08-19 o banco roda em modo WAL de verdade** (ver docs/CHANGELOG.md — sem WAL, um sync de catálogo travava o app inteiro), então essa cópia sidecar deixou de ser só defensiva. Risco conhecido, não tratado ainda: a cópia dos dois arquivos não é atômica entre si (ver comentário em `backup.ts`). Poda mantendo os 10 backups mais recentes.
- **Agendamento**: `setInterval` simples no Main process, sem `@nestjs/schedule` (isso não vive no Nest) — um backup no boot se não houver nenhum do dia, depois a cada 6h. Chamado em `boot()` só depois de `startBackend()` confirmar `/health` (banco já em estado consistente, migrations aplicadas).
- **`restoreBackup(fileName)`**: não dá pra sobrescrever o `.db` com o backend rodando (lock do SQLite) — para o processo filho (`stopBackend()`), copia o backup escolhido por cima do banco atual, religa (`startBackend()`) e recarrega a janela (`mainWindow.reload()`). **Rede de segurança**: cria um backup do estado ATUAL antes de sobrescrever — se o arquivo escolhido for o errado, o estado imediatamente anterior ao restore não se perde.
- **IPC** (`backup-ipc.ts`, mesma convenção `domínio:ação`): `backup:create`, `backup:list`, `backup:restore`. `registerBackupIpc()` recebe `stopBackend`/`startBackend`/`reloadWindow` como parâmetros injetados em vez de importar o estado privado de `index.ts` diretamente — mesmo desacoplamento de `registerHardwareIpc()`.
- **Frontend**: seção "Backup local" em `settings-dialog.tsx` (lista com data/tamanho, botão "Fazer backup agora", "Restaurar" por item com confirmação explícita em duas etapas avisando que é destrutivo e não pode ser desfeito — mesmo padrão de cautela do motivo obrigatório do estorno de venda, Sprint 14). Fora do Electron (`window.easypdv` indisponível), mostra a mesma mensagem de indisponibilidade já usada pra hardware — confirmado que a seção não tenta chamar `window.easypdv` fora do Electron (`enabled: isElectron()` no hook de listagem).
- **Só testável de verdade dentro do Electron** — `window.easypdv` não existe em `next dev` puro (mesma limitação documentada pra hardware, Sprint 11). O fluxo de criar/listar/restaurar contra o app real (dev do Electron ou empacotado) fica pendente de validação na próxima sessão; confirmado nesta sprint apenas que a degradação fora do Electron não gera erro no console.

## Segurança

`contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, módulo `remote` desabilitado, whitelist explícita de canais IPC (`activation:completed`, `printer:print`, `drawer:open`, `printers:list`, `settings:get`, `settings:set`, `backup:create`, `backup:list`, `backup:restore`), CSP estrita na `BrowserWindow` (ainda não configurada explicitamente — TODO antes do lançamento). Sem ícone próprio (`resources/icon.ico`) ainda — `electron-builder` usa o ícone genérico padrão; branding real é decisão do usuário, fora do escopo desta sprint.
