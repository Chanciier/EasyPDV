### CI real corrigido pela primeira vez (2026-08-15) — estava quebrado desde a criação
Descoberto ao investigar um alerta do usuário sobre push pra `main` falhando: o workflow `.github/workflows/ci.yml` **nunca passou, nem uma vez, desde que foi criado** (Sprint 0) — todo `git push` pra `main` desde então (Sprint 5 em diante, no histórico visível) falhava em segundos, antes de qualquer lint/typecheck/build rodar de verdade. Três bugs reais, empilhados um atrás do outro, só visíveis rodando o CI de verdade (não em `pnpm -w typecheck/lint/build` local, que sempre "passava" porque o ambiente de dev já tinha os Prisma Clients gerados de sessões anteriores):
1. **`pnpm/action-setup@v4` recusava rodar** com a versão do pnpm especificada em dois lugares ao mesmo tempo (`version: 11` no YAML do workflow + `packageManager: "pnpm@11.16.0"` no `package.json`) — `Error: Multiple versions of pnpm specified`. Corrigido removendo a duplicata do YAML; `packageManager` já é a fonte única de verdade.
2. **Node 20 no runner, mas pnpm 11 exige Node ≥22.13** (usa o módulo nativo `node:sqlite`, adicionado no Node 22.13) — `Error [ERR_UNKNOWN_BUILTIN_MODULE]: No such built-in module: node:sqlite`, o próprio pnpm quebrava antes de instalar qualquer coisa. Corrigido subindo `node-version` pra 22 no workflow; `package.json#engines.node` também corrigido de `>=20` pra `>=22.13` (o valor antigo deixaria alguém reproduzir o mesmo crash localmente).
3. **Prisma Client nunca era gerado no CI** — nem `pdv-backend` nem `intermediador` têm `postinstall`, e `pnpm install --frozen-lockfile` sozinho não roda `prisma generate`. Todo model adicionado desde o schema inicial falhava o typecheck no CI com `Module '"@prisma/client"' has no exported member 'X'` — mascarado localmente porque toda sessão de dev já roda `prisma migrate dev` manualmente (que gera o client como efeito colateral) antes de validar. Corrigido adicionando `pnpm --filter @easypdv/pdv-backend run prisma:generate` e o mesmo pro intermediador, antes de lint/typecheck/build — não precisa de `DATABASE_URL` nem Postgres real, `prisma generate` só lê o schema.

**Confirmado corrigido rodando o CI de verdade** (`gh run watch`), não só lendo o YAML: run [31897607861](https://github.com/Chanciier/EasyPDV/actions/runs/31897607861) passou checkout → pnpm/node setup → install → os dois `prisma:generate` → lint → typecheck → build → test, todos verdes, 1m10s — primeira vez que isso acontece no projeto.

**Lição mais ampla**: `pnpm -w typecheck/lint/build` rodando limpo localmente nunca provou que CI funcionava — o ambiente de dev acumula estado (Prisma Clients gerados, versões de Node/pnpm já corretas) que o CI, partindo de uma checkout limpa, não tem. Terceira variação da lição repetida desde a Sprint 1 ("só testar em dev não prova que o pacote final funciona"): aqui o "pacote final" era o próprio pipeline de CI, e ninguém tinha rodado `gh run list` pra notar que ele nunca tinha passado.

### Sprint 12 — Fiscal: emissão de NFC-e via Bling
- **Pesquisada a API real de NFC-e do Bling antes de implementar** (mesma metodologia da Sprint 7 — spec OpenAPI pública + código-fonte da lib de terceiro `bling-erp-api-js` no GitHub): `POST /pedidos/vendas/:id/gerar-nfce` gera a NFC-e a partir do pedido de venda já criado, sem precisar de dados fiscais (NCM/CFOP/CST) no schema local — o Bling resolve isso do cadastro do produto do lado dele. Isso só cria um rascunho ("Pendente"); `POST /nfce/:id/enviar` é a chamada que de fato transmite pra SEFAZ.
- **Emissão é opt-in via `BLING_NFCE_AUTO_EMIT`** (env var no Intermediador, default desligado) — decisão deliberada de segurança: emitir NFC-e é uma ação fiscal real, não reversível como criar um "pedido de venda" de teste. Sem essa flag, nenhuma loja passa a emitir documentos fiscais reais só por ter o Bling conectado — precisa ser ligada conscientemente depois que a conta Bling estiver configurada pra NFC-e (certificado digital, inscrição estadual).
- **`FiscalDocument` em dois bancos**: Intermediador (Postgres, rastreamento operacional completo — `externalId`, `externalStatus` numérico bruto do Bling, `errorMessage`) e PDV local (SQLite, espelho simplificado por venda, consultado sob demanda). `GET /fiscal/sale/:saleId` no Intermediador (guardado por `TerminalApiKeyGuard`, mesmo padrão de `POST /sync`) é o que o PDV local chama; `GET /sales/:saleId/fiscal` no PDV local é o que o frontend consome.
- **Falha na emissão nunca bloqueia a venda nem o `SyncJob`**: o pedido de venda já foi criado com sucesso antes da etapa de NFC-e rodar — "fiscal pode esperar" (decisão já registrada desde o início do projeto). Erro fica visível via `FiscalDocument.status=error` + `errorMessage`, sem retry automático nesta sprint. Se o Intermediador estiver inacessível na hora da consulta, o PDV local cai pro que já está espelhado localmente em vez de falhar a tela de Histórico.
- **Bug de idempotência corrigido antes de existir de fato**: adicionar passos depois da criação do pedido de venda (`BlingSyncTargetAdapter.process()`) abriu uma janela nova de retry-após-sucesso-parcial que não existia antes — se a etapa de NFC-e falhasse e o `SyncJob` fosse reprocessado, o pedido de venda seria criado de novo no Bling (`createSalesOrder` não é idempotente, achado documentado desde a Sprint 8). Corrigido checando o `ErpSyncMapping` (sale→externalId) **antes** de chamar `createSalesOrder`, não só depois — mesmo padrão já usado pra produto/contato.
- **Badge de status fiscal na tela de Histórico** (`components/pos/history-view.tsx`): pending/issued/cancelled/error, com link pro DANFE quando emitida e a mensagem de erro quando rejeitada. Testado de verdade no navegador semeando um `FiscalDocument` local pra cada um dos quatro status e confirmando a renderização de cada um.
- Testado ponta a ponta em navegador real (login, venda confirmada, `GET /sales/:id/fiscal` retornando `200 null` quando não há documento fiscal — comportamento normal em V1 com a flag desligada, exercitando o fallback de rede já que o Intermediador não estava rodando durante o teste). Confirmado também que o `FiscalController` do Intermediador rejeita chamadas sem `X-Terminal-Api-Key` válida (401) e que o boot completo do Intermediador resolve a injeção de dependência nova sem erro (gotcha de guard já documentado desde a Sprint 10). **Emissão real de NFC-e contra a conta Bling do usuário não foi testada nesta sprint** — reconectar o Bling (OAuth) e ligar `BLING_NFCE_AUTO_EMIT` de verdade fica pra quando o usuário confirmar que a conta está configurada pra NFC-e; é uma ação fiscal real, não um teste reversível. `pnpm -w typecheck`, `lint` e `build` passam nos 11 pacotes do monorepo.

### Sprint 11 — Hardware: impressora, gaveta, leitor de código de barras
- **Impressão ESC/POS raw via WinSpool**: `apps/electron/src/main/hardware/` — `PrinterDriver` interface + `WindowsRawPrinterDriver` (envia bytes crus pro spooler do Windows via `resources/print-raw.ps1`, P/Invoke de `winspool.drv`, padrão KB Q322090) e `MockPrinterDriver` (loga em vez de imprimir, usado sem impressora configurada ou com `EASYPDV_PRINTER_MOCK=1`). Escolhido PowerShell + .NET embutido em vez de addon nativo Node (`node-printer`, `ffi-napi`) de propósito — evita dependência de compilação nativa não testada na máquina real do cliente.
- **Testado de verdade contra a impressora de referência cadastrada nesta máquina** (`ELGIN L42PRO FULL`, USB): `WritePrinter` retornou sucesso e o job apareceu na fila real de impressão do Windows como "EasyPDV Raw Print" (confirmado via `Get-PrintJob`, depois limpo com `Remove-PrintJob`). A impressora física ainda não está conectada (só será conectada quando o usuário tiver acesso ao terminal) — confirmação de papel saindo/corte/pulso de gaveta é um risco aberto conhecido, não um bug (mecanismo de envio confirmado funcionando, consumo físico pendente).
- **Formatador de cupom** (`hardware/escpos.ts`, `hardware/receipt-formatter.ts`): comandos ESC/POS mínimos (init, alinhamento, negrito, corte parcial, pulso de gaveta no pino 2 — ligação mais comum via kick-out integrado da impressora). Texto em ASCII puro (acentos removidos) — térmicas ESC/POS usam code pages de 1 byte que variam por impressora, sem saber qual está configurada em cada cliente, remover acento é mais seguro que arriscar caractere ilegível.
- **IPC de hardware + preload bridge**: canais `printer:print`, `drawer:open`, `printers:list`, `settings:get`, `settings:set` (convenção `domínio:ação` já estabelecida). `HardwareSettings` persiste em `app.getPath("userData")/settings.json`. Contratos (`ReceiptPrintPayload`, `HardwareSettings`) em `packages/shared-types/src/electron.ts`, único entre Main e Renderer.
- **Tela de Configurações no frontend** (`components/pos/settings-dialog.tsx`, aberta pelo ícone de engrenagem na sidebar) — pedido explícito do usuário ao saber que a impressora só seria conectada fisicamente mais tarde: escolher a impressora cadastrada no Windows, dois toggles de automação (imprimir recibo / abrir gaveta em venda em dinheiro), botões "Imprimir teste"/"Abrir gaveta" pra validação manual assim que o hardware for conectado. Fora do Electron (`window.easypdv` indisponível), mostra aviso e desabilita "Salvar" — confirmado rodando no navegador.
- **Impressão/gaveta automática na confirmação de venda** (`sale-view.tsx`): dispara via `mutate()` (não `mutateAsync()`) — nunca bloqueia nem falha a venda, que já foi confirmada no backend antes disso rodar.
- **Captura global de leitor de código de barras USB** (emulação de teclado, sem IPC — direto no Renderer, só na tela Venda): sem input/select/textarea focado e sem diálogo de pagamento/recibo aberto, o primeiro caractere digitado foca a busca e é encaminhado manualmente; o resto do código + Enter reaproveita o fallback de leitura exata já existente (`findProductByBarcode`).
- **Bug real encontrado e corrigido rodando de verdade no navegador**: sem `e.preventDefault()`, mover o foco pro input de busca *dentro* do handler de keydown fazia o navegador aplicar a inserção nativa de texto no elemento recém-focado (não no que originou o evento) — duplicando o primeiro caractere digitado (`"77"` em vez de `"7"`). Corrigido chamando `preventDefault()` antes de mudar o foco; confirmado com um código de barras real do catálogo de seed (`7891000000011`, "Arroz 5kg") lido corretamente do início ao fim e o produto certo adicionado ao carrinho.
- Testado ponta a ponta em navegador real (`next dev` + `pdv-backend` real, sem Electron — o que dá pra testar sem o bridge real): login, Settings mostrando indisponibilidade fora do Electron corretamente, leitura de código de barras real via captura global, venda completa em dinheiro com recibo, sem erros no console. `pnpm -w typecheck`, `lint` e `build` passam nos 11 pacotes do monorepo.

### Sprint 10 — Electron: empacotamento, provisionamento de terminal, auto-update
- **`pdv-backend` sobe como processo filho de verdade do Electron**, não mais um servidor que o operador liga manualmente: `startBackend()` (Main process) spawna `dist/main.js` via `spawn(process.execPath, ..., { ELECTRON_RUN_AS_NODE: "1" })` — o próprio binário do Electron roda como Node puro, sem exigir Node instalado na máquina do cliente. `DATABASE_URL` aponta pra `app.getPath("userData")/easypdv.db`, isolado por instalação.
- **Auto-migração no boot**: `pdv-backend/src/main.ts` roda `prisma migrate deploy` (resolvendo a CLI via `require.resolve`, funciona tanto com symlink do pnpm quanto num bundle achatado) antes de escutar a porta — idempotente, roda todo boot. Testado de verdade contra um banco genuinamente novo: `pnpm start` (Electron em dev) criou `easypdv.db` do zero em `app.getPath("userData")` e aplicou as 7 migrations existentes sozinho, sem intervenção manual.
- **Provisionamento de terminal, ponta a ponta e testado com curl real** (não simulado): Intermediador ganhou o módulo `organizations` — `ActivationCode` (código de 8 caracteres sem 0/O/1/I/L, expira em 30min, uso único, `UPDATE` condicional evita corrida em duas ativações simultâneas com o mesmo código — mesmo padrão do retry de SyncJob da Sprint 8) e `Terminal` (`apiKeyHash` SHA-256, não bcrypt — a apiKey já nasce alta-entropia via `crypto.randomBytes`, o problema aqui é lookup rápido por índice único, não resistência a senha de baixa entropia). `POST /organizations` → `POST /organizations/:id/activation-codes` → `POST /terminals/activate` testado de ponta a ponta: geração de código, ativação com sucesso, reuso do mesmo código (409), código inválido (404). PDV local ganhou `StoreIdentity` (já existia no schema desde o Sprint 0, sem módulo nenhum até agora) com `GET /provisioning/status` + `POST /provisioning/activate`, chamando o Intermediador de verdade e persistindo o resultado localmente.
- **Fecha o risco #6 de Decisões e Riscos Abertos** (autenticação PDV local ↔ Intermediador inexistente, aberto desde a Sprint 6): `POST /sync` agora exige `X-Terminal-Api-Key` (`TerminalApiKeyGuard`) — `storeId` do `SyncJob` passa a vir do terminal autenticado, não mais um campo confiável vindo do body. Testado com uma venda real confirmada: sale → outbox → `POST /sync` autenticado → `SyncJob` criado com o `storeId` correto do terminal ativado (só o passo seguinte, chamada real ao Bling, falhou — esperado, credenciais placeholder de dev). `GET/POST /sync/jobs*` (Central de Erros, Sprint 8) seguem sem auth de propósito — são visibilidade/retry pra um administrador, não uma chamada de terminal, e não existe auth de admin no Intermediador ainda (risco separado, permanece aberto).
- **UI de ativação de terminal**: `resources/activation.html`, página standalone (não é parte do build do Next.js) carregada pelo Main quando `GET /provisioning/status` retorna `activated:false`. Após ativar com sucesso, chama `window.easypdv.activationCompleted()` (preload → IPC) — é o Main quem decide trocar pra janela do app real, a página não tem esse poder sozinha (contextIsolation).
- **Auto-update com bloqueio de caixa aberto**: `electron-updater`, checagem no boot + a cada 4h. Antes de instalar uma atualização já baixada, consulta `GET /provisioning/busy-status` (endpoint novo, sem auth — qualquer `CashSession` aberta em qualquer caixa do terminal, não escopado por operador); se ocupado, reavalia a cada 10min em vez de esperar o próximo ciclo de 4h inteiro.
- **Empacotamento real via `pnpm deploy`**: `pnpm --filter @easypdv/pdv-backend deploy --prod --legacy` monta um `node_modules` autocontido (sem symlink do pnpm store, que o processo filho spawnado não entenderia) — confirmado gerando o bundle de verdade, incluindo o engine nativo do Prisma pra Windows (`prisma generate` rodado de novo dentro do bundle, já que `pnpm deploy` não roda esse postinstall sozinho). `dev.db` e `.env` são removidos do bundle antes de empacotar — artefato de dev não vai pro instalador.
- **Bug real encontrado testando o `.exe` empacotado de verdade** (não apareceria em `pnpm start` dev, só no bundle deployado): `nestjs-pino` tentava carregar o transport `pino-pretty` no boot e crashava — `LoggerModule.forRoot` só usa esse transport quando `NODE_ENV !== "production"`, e como o Electron nunca setava `NODE_ENV` ao spawnar o processo filho, o backend achava que estava em dev. Só que `pino-pretty` é `devDependency` (formatação de log legível no terminal, sem uso num processo gerenciado pelo Electron) — `pnpm deploy --prod` corretamente a excluiu do bundle, e o app quebrava no primeiro boot tentando usar um módulo que não existia. Corrigido setando `NODE_ENV: app.isPackaged ? "production" : "development"` no `env` do `spawn()`. Confirma a lição da Sprint 1 de novo: só testar em dev não prova que o pacote final funciona.
- **Dois bugs reais adicionais encontrados no mesmo teste do `.exe` empacotado**, ambos silenciosos em dev porque o `.env` local mascarava o problema: (1) `JWT_SECRET` é `getOrThrow` no `IdentityModule` — sem o `.env` de dev (removido do bundle de propósito), o backend crashava no boot com um diálogo de erro nativo do Electron. Corrigido gerando a secret uma vez por instalação (`crypto.randomBytes(48)`) e persistindo em `app.getPath("userData")/jwt-secret` — nunca hardcoded no código (senão toda instalação do EasyPDV compartilharia a mesma chave de assinatura de token, permitindo forjar token válido pra qualquer loja cliente). (2) Nenhum install novo tem usuário nenhum — `prisma db seed` é só fixture de dev (catálogo/depósito de exemplo) e não roda em produção, mas sem seed nenhum administrador consegue logar (não existe fluxo de "criar conta"). Corrigido chamando só a parte de criação do admin (`ensureAdminUser`, idempotente, mesma lógica de `prisma/seed.ts`) direto no `bootstrap()` do Nest, sempre. **Risco aberto**: a senha ainda é o mesmo placeholder de dev (`SEED_ADMIN_PASSWORD`/default "troque-esta-senha") — não existe troca de senha obrigatória no primeiro login, cada instalação real nasce com uma senha padrão conhecida até esse fluxo ser construído (ver Decisões e Riscos Abertos).
- **Duas limitações de ambiente encontradas e documentadas** (não são bug do produto): `electron-builder` tenta baixar o zip do Electron de `release-assets.githubusercontent.com`, host instável nesta sandbox de desenvolvimento específica — contornado com `ELECTRON_OVERRIDE_DIST_PATH` apontando pro binário que o pacote `electron` já baixa sozinho durante `pnpm install`. E a extração do `winCodeSign` (ferramentas de assinatura, baixadas mesmo sem certificado) falha por falta de privilégio de symlink do Windows nesta sessão — contornado com `win.signAndEditExecutable: false` (não estamos assinando o instalador ainda, sem certificado). Nenhuma das duas deve ocorrer numa máquina de desenvolvimento normal.
- **`prisma` (CLI) movido de devDependencies pra dependencies** no `pdv-backend` — precisa estar disponível em runtime no bundle empacotado pra rodar `migrate deploy` no boot; um `pnpm deploy --prod` não inclui devDependencies.
- Bug real pré-existente: `pnpm run <script>`/`pnpm exec` disparam a checagem de estado de dependências do pnpm 11 sempre que `package.json` muda sem `pnpm install` correspondente — em ambiente não-interativo (sem TTY) isso aborta com `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY` em vez de perguntar. Uma tentativa de contornar isso com `CI=true` acabou rodando um `pnpm install --production` que **apagou as devDependencies de `apps/electron`** (incluindo o próprio `electron-builder`) — recuperado com `pnpm install` completo na raiz. Lição: `CI=true` é seguro pra destravar prompts, mas não neutraliza o efeito de um `install --production` já em andamento; chamar o binário em `node_modules/.bin/` direto evita o `pnpm exec`/`pnpm run` que dispara a checagem.

### Sprint 9 — Frontend: migração do mock para a API real
- **`apps/pdv-frontend` passa a consumir `apps/pdv-backend` de verdade** nas telas Venda, Caixa, Produtos e Histórico — TanStack Query pro estado de servidor, Zustand (`useAuthStore`, `useCartStore`) pro estado de UI/rascunho. Clientes segue mock (ver docs/FRONTEND.md, seção "Escopo cortado" — não existe módulo de Clientes no backend ainda).
- **Autenticação**: `useAuthStore` (Zustand + persist) guarda tokens; `lib/api-client.ts` injeta Bearer e faz refresh-on-401 com dedup (várias requisições caindo em 401 ao mesmo tempo disparam uma única troca de refresh_token — confirmado em teste real com 4 requisições concorrentes, só 1 `POST /auth/refresh`). Guarda de rota 100% client-side (`app/page.tsx`) — sem middleware, o export é estático.
- **Backend ganhou `app.enableCors()`** — necessário pro frontend (porta 3000) chamar o backend (porta 4001) em origens diferentes; autenticação é Bearer token, não cookie, então CORS aberto não expõe sessão.
- **Três endpoints novos no Catalog**, todos por uma necessidade real do frontend descoberta durante a migração (não especulativos): `GET /products/:id` (resolver nome de produto a partir de `SaleItem.productId`, que só guarda o id), `GET /price-lists/active` (a tela Produtos precisa do id da tabela de preço pra gravar `POST /price-lists/:id/items`), e já existia `GET /sales`/`GET /cash/sessions/:id/movements` (adicionados junto com o CORS, no mesmo commit desta sprint).
- **Bug real pré-existente encontrado e corrigido**: `CloseCashSessionUseCase` calculava `expectedAmount` sem somar as vendas em dinheiro da sessão — um comentário no código dizia "a partir da Sprint 5" mas nunca foi feito mesmo depois do Payment existir. Corrigido somando `sumCashPayments(cashSessionId)` (agregação no `PrismaSaleRepository`) à fórmula; descoberto construindo a tela de Caixa real, não é regressão desta sprint.
- **Tela de Venda**: fluxo completo contra o backend real (`POST /sales` lazy-start no primeiro item → `POST /sales/:id/items` → `POST /sales/:id/payments` → `POST /sales/:id/confirm`). Sem endpoint de "trocar quantidade" na API — contornado com `DELETE` + `POST` (ver docs/FRONTEND.md). Busca por nome/SKU com preço resolvido em paralelo (`useQueries`); leitura de código de barras cai no fallback `GET /products/by-barcode/:code` quando a busca textual não encontra nada (busca não indexa código de barras). `Esc` sem foco em campo de texto cancela a venda em rascunho de verdade (`POST /sales/:id/cancel`), não só limpa estado local.
- **Tela de Caixa**: reescrita contra `useCash*` hooks reais; "vendas (dinheiro)" é derivado client-side de `GET /sales?cashSessionId=&status=confirmed` (sem endpoint agregado dedicado). Fechamento com modal de conferência (valor contado vs. esperado), não mais um clique direto usando o valor esperado como se fosse o contado.
- **Tela de Produtos**: CRUD real via Catalog API — criar/editar produto, categoria (com criação inline), preço (via tabela ativa) e adicionar código de barras. "Excluir" é sempre `PATCH /products/:id { active:false }` — não existe hard delete (SKU pode estar em vendas já confirmadas) nem endpoint pra listar produtos inativos, então desativar é hoje uma via de mão única pela UI.
- **Tela de Histórico**: lista `GET /sales?status=confirmed` com detalhe por cupom (itens, pagamentos, total) — nomes de produto resolvidos via `GET /products/:id`, batched por `useQueries`.
- Testado ponta a ponta em navegador real contra o backend real (não simulado): login → 4 refreshes concorrentes deduplicados → abrir caixa → venda completa (busca, +/-, pagamento dinheiro com troco, confirmação, recibo) → saldo do caixa atualizado automaticamente (invalidação de cache) → leitura de código de barras via fallback → cancelamento de rascunho via Esc → criar produto com categoria nova + preço + código de barras → editar e desativar produto → Histórico mostrando a venda recém-confirmada com nome de produto resolvido.
- `pnpm -w typecheck`, `lint` e `build` passam nos 11 pacotes do monorepo (incluindo `next build` do export estático).

### Sprint 8 — Central de Erros de Sincronização + reconciliação
- **Visibilidade e retry manual dos dois lados**: `GET /sync/outbox?status=` + `POST /sync/outbox/:id/retry` no PDV local; `GET /sync/jobs?status=` + `POST /sync/jobs/:id/retry` no Intermediador. Retry só aceita entradas/jobs "failed" (409 caso contrário, 404 se não existir).
- **`SyncJobReconciliationWorker`** (Intermediador, `@nestjs/schedule` `@Interval` a cada 2min): encontra `SyncJob`s travados em "processing" há mais de 5min (worker morreu ou Redis perdeu o job no meio do processamento) e marca "failed" com `lastError` explicando o motivo — não reenfileira sozinho, por design (reconciliação é manual, ver docs/ROADMAP.md). Resolve o risco #4 rastreado desde a Sprint 6/7 (perda de job em fila sem varredura de recuperação).
- **Bug real de concorrência encontrado e corrigido durante o teste** (não hipotético — reproduzido com duas requisições HTTP concorrentes de verdade): `POST /sync/jobs/:id/retry` chamado duas vezes rapidamente enfileirava dois jobs BullMQ em paralelo pro mesmo `SyncJob`, e como `createSalesOrder` não é idempotente, isso podia criar pedidos duplicados no Bling. Corrigido trocando `findById` + `update` incondicional por um `UPDATE` condicional atômico (`WHERE id=? AND status='failed'`) — mesma correção aplicada em `POST /sync/outbox/:id/retry` por consistência.
- Testado ponta a ponta com Postgres+Redis reais: retry de entrada/job "failed" (sucesso), retry de algo que não está "failed" (409), retry de id inexistente (404), duas requisições de retry concorrentes na mesma entrada/job (só uma vence, confirmado via log — só uma sequência de tentativas, sem duplicação), job seedado artificialmente travado em "processing" há 10min reconciliado pela varredura real no primeiro tick do `@Interval`.

### Sprint 7 — Adapter Bling (sincronização real ponta a ponta)
- **Fluxo OAuth2 completo e testado contra o Bling real**: `GET /integrations/bling/connect?organizationId=` gera o link de autorização (`state` codifica o organizationId, base64url); `GET /integrations/bling/callback` troca o `code` por token via `www.bling.com.br/Api/v3/oauth/token` (HTTP Basic client_id:client_secret) e grava em `ErpIntegration`; `BlingTokenProviderService` renova automaticamente via refresh_token quando o access_token está a menos de 60s de expirar — o Bling rotaciona o refresh_token a cada uso, os dois tokens são sempre persistidos juntos.
- Modelos `ErpIntegration` (credenciais OAuth por organização) e `ErpSyncMapping` (cache de IDs externos: produto por SKU, "Consumidor Final", venda→pedido) no Intermediador.
- `BlingApiClient`: `GET /produtos?codigo=`, `GET/POST /contatos`, `POST /pedidos/vendas` — confirmados contra `api.bling.com.br/Api/v3` real, não só a spec pública.
- **`BlingSyncTargetAdapter implements SyncTargetPort`** substitui o `NoopSyncTargetAdapter` da Sprint 6 sem tocar no `SyncProcessor` nem nos use-cases — exatamente a troca que a arquitetura Ports & Adapters foi desenhada pra permitir. Resolve produto por SKU (cacheado em `ErpSyncMapping`), contato padrão "Consumidor Final" (busca ou cria, cacheado), e cria o pedido de venda no Bling.
- Payload do `SyncOutbox`/`SyncJob` para `entityType="sale"` (Sprint 6) enriquecido com `sku`, `name` e `unitPrice` por item — o Intermediador nunca acessa o Catalog local, precisava desses dados "achatados" pra resolver o produto no Bling. Tipo `SaleSyncPayload` centralizado em `@easypdv/shared-types` pra manter os dois lados em sincronia.
- **Descoberta real durante o teste**: Bling não expõe endpoint de listagem de formas de pagamento (suposição inicial errada) — o id (`BLING_DEFAULT_PAYMENT_METHOD_ID`) vem de configuração, obtido manualmente no painel do Bling ou inspecionando um pedido existente via `GET /pedidos/vendas/:id`. V1 usa uma única forma de pagamento fixa pra todo pedido, independente da forma real da venda local — simplificação documentada, não bloqueia a V1.
- **Testado ponta a ponta contra o Bling real do usuário** (não simulado): venda confirmada no pdv-backend → outbox → `SyncJob` → `BlingSyncTargetAdapter` → pedido de venda criado de verdade no Bling (conferido campo a campo via `GET /pedidos/vendas/:id`: contato, itens, quantidade, valor unitário, total e forma de pagamento todos batendo com a venda local).
- `docs/BACKEND.md` ganhou uma seção sobre o padrão de client gerado próprio por app em monorepos Prisma (lição da Sprint 6, reaproveitada aqui sem repetir o bug).

### Sprint 6 — Outbox, Fila e Workers
- **PDV local**: modelo `SyncOutbox` (transactional outbox) — `PrismaSaleRepository.confirm()` grava uma entrada `entityType="sale"` na mesma transação do `SaleConfirmed` (mesma exceção pragmática já usada pro débito de estoque). `SyncOutboxWorker` (`@nestjs/schedule`, a cada 15s) varre entradas `pending` e faz `POST /sync` no Intermediador via `HttpSyncGateway`; sucesso marca `synced`, falha incrementa `attempts` e retenta (teto de 5 antes de virar `failed`). Endpoint `GET /sync/outbox` para visibilidade/depuração.
- **Intermediador**: modelo `SyncJob` (Postgres) + fila BullMQ (`@nestjs/bullmq`, Redis). `POST /sync` cria (ou reaproveita, idempotente por `@@unique([entityType, entityId])`) um `SyncJob` e enfileira; `SyncProcessor` (worker BullMQ) processa cada job via `SyncTargetPort` — Sprint 6 só tem o `NoopSyncTargetAdapter` (loga e confirma "synced", sem falar com nenhum ERP de verdade), Sprint 7 substitui pelo Adapter Bling sem tocar no processor. `GET /sync/jobs/:id` consulta status.
- Scaffolding base do Intermediador completado: `PrismaModule`/`PrismaService`, `ConfigModule`, `BullModule`, `DomainError`/`DomainExceptionFilter` — mesmo padrão já usado no pdv-backend.
- **Bug real de monorepo encontrado e corrigido**: pdv-backend e intermediador compartilham a mesma versão de `@prisma/client`, que o pnpm deduplica numa única pasta física — `prisma generate` de um app sobrescrevia o client gerado do outro (schemas diferentes, mesmo destino), quebrando em runtime quem não gerou por último. Só apareceu ao rodar os dois servidores juntos pela primeira vez (nenhuma sprint anterior precisou disso). Corrigido dando ao intermediador um `output` próprio (`src/generated/prisma`) no `generator client`, com ajustes em `tsconfig.json` (exclude), `nest-cli.json` (assets copiados pro `dist/`) e `eslint-config` (`**/generated/**` ignorado). Ver docs/BACKEND.md.
- `docker-compose.yml`: portas de Postgres/Redis viraram configuráveis via env (`POSTGRES_PORT`/`REDIS_PORT`, default 5433/6380) — a máquina de dev já tinha outro projeto ocupando 5432/6379.
- Testado ponta a ponta manualmente com Postgres+Redis reais via Docker: venda confirmada → outbox local `synced` → `SyncJob` criado e processado (`synced`, 1 tentativa) no Intermediador → reenvio do mesmo `entityId` não duplica o job (idempotência confirmada) → `GET /sync/jobs/:id` inexistente retorna 404.
- **Gap aberto e documentado**: `POST /sync` sem autenticação (provisionamento de terminal é Sprint 10); varredura de reconciliação para `SyncJob`s órfãos por perda do Redis fica pra Central de Erros de Sincronização (Sprint 8). Ver docs/ERROR-HANDLING.md.

### Sprint 5 — Pagamentos + Confirmação
- Modelo `Payment` (method: dinheiro/cartao/pix/outro; status: aprovado/pendente/recusado — em V1 sem TEF/gateway real, cartão entra direto "aprovado" pois a maquininha física já aprovou, ver docs/ROADMAP.md).
- `RegisterPaymentUseCase`: registra pagamento numa venda em draft.
- `ConfirmSaleUseCase`: exige venda em draft, com itens, e pagamentos aprovados cobrindo o total (`InsufficientPaymentError` caso contrário); resolve o depósito padrão via `ListWarehousesUseCase` (exportado pelo `InventoryModule`, mesmo padrão de injeção cross-módulo já usado com `ResolvePriceUseCase` na Sprint 4).
- **Evento central `SaleConfirmed` implementado**: `PrismaSaleRepository.confirm()` atualiza `Sale.status` para `confirmed` e debita o estoque de cada item (`StockMovement` tipo "venda" + `StockItem.decrement`) numa única transação Prisma — exceção deliberada e documentada à separação estrita de dados por módulo, justificada pela exigência de atomicidade (a camada de use-case continua dependendo só de `SaleRepositoryPort`).
- **Race condition de estoque resolvida** (risco aberto desde a Sprint 3): débito via `{ decrement: n }` do Prisma (SQL `UPDATE ... SET quantity = quantity - n` atômico) em vez de read-modify-write em código de aplicação; combinado com a serialização de escrita do SQLite, elimina a corrupção quando dois caixas confirmam o mesmo produto ao mesmo tempo. Validado empiricamente: duas confirmações simultâneas debitando 5 unidades cada de um estoque de 60 resultaram em 50, com dois `StockMovement` distintos — nenhuma escrita perdida. Ver docs/ERROR-HANDLING.md.
- Endpoints: `POST /sales/:id/payments`, `POST /sales/:id/confirm`.
- Testado ponta a ponta manualmente: confirmação de venda sem itens (409), sem pagamento (409), com pagamento parcial (409), pagamento completo + confirmação (201, estoque debitado, `StockMovement` conferido), reconfirmação de venda já confirmada (409), e o teste de concorrência descrito acima.

### Sprint 4 — Caixa e Venda (núcleo)
- Módulo Sales completo em `apps/pdv-backend` (bundla Caixa + Venda, conforme docs/MODULES.md): CashRegister, CashSession, CashMovement, Sale, SaleItem.
- Caixa: abrir sessão (409 se já existe uma aberta no registrador), sangria/suprimento/ajuste, fechar com cálculo automático de `expectedAmount` (abertura + suprimento - sangria + ajuste), sessão atual do operador.
- Venda: iniciar (draft, exige sessão de caixa aberta), adicionar/remover item (preço resolvido via `CatalogModule.ResolvePriceUseCase`, exportado para consumo entre módulos), cancelar — total recalculado a cada mudança de item.
- **Escopo deliberadamente limitado**: sem desconto, sem Payment, sem confirmação — venda só transita entre `draft` e `cancelled`. `confirmed` + débito de estoque + Payment entram juntos na Sprint 5, numa única transação atômica (é o "evento central" `SaleConfirmed` documentado desde o início).
- Seed estendido com um `CashRegister` ("Caixa 1").
- Testado ponta a ponta manualmente: abrir/duplicar-caixa (409), sangria/suprimento, iniciar venda, adicionar 2 itens (total conferido), remover item (total recalculado), cancelar (imutabilidade depois confirmada com 409), fechar caixa com divergência zero conferida.
